#### FAQ-CHK101

**Title:** Graph Translation Failure

**Error Code:**
```
GRAPH_TRANSLATE_FAILED (101)
```

**Key Log:**
```
[GenGraph] [ErrorCode: 101] Failed to convert one task into a graph node, taskIndex=128, ret=1, taskMeta=taskType=0, rankId=3, streamId=7, srcRankId=3, dstRankId=4, src=[0x0,0x400), dst=[0x1000,0x1400), protocol=1
```

**Symptom:** The graph generation phase cannot translate the input task meta into an internal graph node. This issue commonly occurs when the task type is not supported or the field combination does not meet the translation conditions.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The `taskType` does not have a corresponding translation implementation.
2. Fields such as `rankId`, `streamId`, offset, and length are abnormal.
3. The task meta generated by the upstream component is itself incorrect.

[Troubleshooting Steps]
Typical error points:
1. A normal task meta cannot be translated into a graph node: first locate the task in the original task list by `taskIndex`; then determine the root cause based on the specific task information.
```

#### FAQ-CHK102

**Title:** Deadlock in Graph Generation Phase

**Error Code:**
```
GRAPH_DEADLOCK (102)
```

**Key Log:**
```
[GenGraph] [ErrorCode: 102] Local Record/Wait matching is stuck on this rank. Some Wait tasks are still blocked, but no new local Record task can unblock them, rankId=0, firstBlockedWaitNode=[TaskWaitAICPU] node=143, rank=0, stream=3, protocol=SDMA, notify={recordRank=0, waitRank=0, notifyId=17}, blockedWaitNodeCount=5
```

**Symptom:** The synchronization pairing process stalls during the graph generation phase. Wait nodes are still waiting, but no new Record nodes can pair with the Wait nodes.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The number of Wait tasks exceeds the number of Record tasks, or Record tasks cannot participate in pairing because other dependencies have not been resolved.
2. The `notifyId` is incorrect. The `notifyId` values of the Wait and Record tasks do not match, so pairing cannot complete.
3. The Record task has already executed, but the predecessor dependencies of the subsequent Wait task are not yet satisfied, so the Wait task cannot enter the pairable queue.

[Troubleshooting Steps]
1. Read the `notifyId`, `recordRank`, and `waitRank` values of `firstBlockedWaitNode` in the log to determine which task should unlock this Wait task.
2. Check whether a matching Record exists on the same rank or the corresponding remote rank. If one exists, continue to verify whether the two tasks can pair correctly.
```

#### FAQ-CHK103

**Title:** Unconsumed Synchronization Pairs Remaining

**Error Code:**

**Symptom:** After synchronization pairing completes, unconsumed synchronization nodes remain. This issue typically manifests as Record nodes that have no corresponding Wait nodes.

2. The `notifyId` in use is incorrect.

[Troubleshooting Steps]

```

#### FAQ-CHK108

**Title:** Register or On-Chip Memory Not Initialized

**Error Code:**
```
GRAPH_REGISTER_UNINITIALIZED (108)
```

**Key Log:**
```
[GenGraphCCU] [ErrorCode: 108] Failed to read XN register before it was initialized, rankId=2, dieId=0, instrId=73, xnId=11

[GenGraphCCU] [ErrorCode: 108] Failed to read HBM content before it was initialized, rankId=2, dieId=0, instrId=73, hbmAddr=0x1000
```

**Symptom:** The current instruction reads a register or on-chip memory content but does not find the corresponding initialized data. This issue typically indicates that the preceding write chain was not established correctly.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The preceding Load / Set / Store instruction has not been executed.
2. The queue responsible for initialization is blocked by a Wait dependency and cannot advance.
3. The address or register resolution is misaligned, causing a read from an incorrect location.

[Troubleshooting Steps]
1. If the log provides an `xnId`, trace back to the most recent valid write to that register in the same queue.
2. If the log provides an `hbmAddr`, check whether a valid write to the corresponding address range exists in earlier tasks.
```

#### FAQ-CHK109

**Title:** ID or Index Out of Range

**Error Code:**
```
GRAPH_OUT_OF_RANGE (109)
```

**Key Log:**
```
[GenGraphCCU] [ErrorCode: 109] dieId is out of range when converting address to MS id, dieId=4, maxDieId=1

[GenGraphCCU] [ErrorCode: 109] Xn register id is out of the valid range, xnId=37, validMin=0, validMax=31
```

**Symptom:** An ID, index, or address ownership field exceeds the current resource or instruction constraint range. This issue commonly occurs when `dieId`, register ID, or intermediate address resolution results go out of range.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The resource pool size does not match the task data. For example, only a subset of dies is loaded.
2. The address ownership resolution is incorrect, mapping a local address to a nonexistent resource ID.
3. The instruction field parsing is misaligned, causing an abnormal register ID or index value.
4. The current data comes from an instruction set of a different version or a different branch.

[Troubleshooting Steps]
1. If the log provides `dieId/maxDieId`, first verify whether the die count in the current resource file matches the task data.
2. If the log provides `xnId/validMin/validMax`, trace back to the original instruction fields to confirm whether the register ID was incorrectly parsed or computed.
```

#### FAQ-CHK110

**Title:** Invalid Address or Alignment Constraint Not Met

**Error Code:**
```
GRAPH_ADDRESS_INVALID (110)
```

**Key Log:**
```
[GenGraphCCU] [ErrorCode: 110] Address does not fall into any known MS address range, localMsAddr=0x27f0000, rawAddr=0x82ff000

[GenGraphCCU] [ErrorCode: 110] Load source address must be 8-byte aligned, sourceAddress=0x1003
```

**Symptom:** The address cannot be mapped to any resource range known to the Checker, or the Load/Store address and length do not meet the alignment constraints of the current instruction.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The base address table does not match.
2. The upstream component wrote an incorrect original address, causing an abnormal value.
3. The upstream address calculation is off.
4. The address or length of an instruction is not aligned as required.

[Troubleshooting Steps]
1. If the log provides `rawAddr/localMsAddr` or `addr/dieBaseAddr`, first determine which resource range the address should theoretically fall into.
2. If the log provides `sourceAddress`, `hbmAddr`, or `dataLengthBytes`, verify whether the 8-byte or 64-byte granularity constraint is met.
```

#### FAQ-CHK404

**Title:** Missing Overwrite Source Semantics

**Error Code:**
```
SEMANTIC_SIMULATE_FAILED (404)
```

**Key Log:**
```
[SemanticCheck] [ErrorCode: 404] Source data needed by this overwrite is missing, dataMapping={operation=overwrite, sourceMemorySlice={rankId=1, memoryType=INPUT, offset=0x0, length=0x800}, targetMemorySlice={rankId=1, memoryType=OUTPUT, offset=0x0, length=0x800}, launchIdx=18446744073709551615, blockId=4294967295, pipeId=4294967295, taskId=4294967295}
```

**Symptom:** The source range semantics required by the overwrite are incomplete. The current semantic implementation continues the simulation but raises a warning that this overwrite does not have "complete memcpy semantics". Subsequent semantic analysis results may be affected.

**Troubleshooting Guidance:**
```
[Possible Causes]
1. The source range of the overwrite was not fully initialized beforehand, or only partial source semantics were established.
2. The source address or length configuration of a preceding transfer or slice task is incorrect, causing the overwrite to read from an empty range where semantics were not established.
3. Some dependent tasks are missing or have an abnormal order, so the corresponding source data is not ready when the overwrite executes.

[Troubleshooting Steps]
1. Use `sourceMemorySlice` to locate the source buffer range that the overwrite reads from, and verify whether complete semantics have been established for that range in preceding tasks.
2. Check the transfer, slice, and reduce tasks before the overwrite to confirm that address ranges are contiguous, lengths match, and no intermediate gaps exist.
